# Phase 4.3 — Confidence Normalization

Implemented under the `SEA_CALIBRATION` feature flag. When the flag is OFF
(default), the engine is byte-identical to v4.9.0 (`REGRESSION=0`, `PARITY=0`,
validation `0/0`). When the flag is ON (`SEA_CALIBRATION=report`), the calibrated
confidence profile is used.

---

## 1. Updated confidence architecture

```
v4.9.0 / v4.10.0 (flag OFF — frozen)          v4.3 (flag ON — calibrated)
─────────────────────────────                  ────────────────────────────
CONFIDENCE dict                                CALIBRATED_CONFIDENCE dict
core/assessment_config.py                      core/assessment_config.py

  BASE_ANCHOR: 50                                BASE_ANCHOR: 50
  CAP_EXPLOITED: 100                             CAP_EXPLOITED: 100
  CAP_VERIFIED: 90                               CAP_VERIFIED: 95   ← raised
  CAP_CONFIRMED: 85                              CAP_CONFIRMED: 95   ← raised
  CAP_LIKELY: 75                                 CAP_LIKELY: 80     ← raised
  CAP_POSSIBLE: 60                               CAP_POSSIBLE: 55   ← lowered
  CAP_ERROR: 40                                  CAP_ERROR: 40      ← unchanged
  (no evidence_quality blend)                    EVIDENCE_QUALITY_WEIGHT: 1.0  ← NEW

profile selection:
  confidence_engine._profile() → CONFIDENCE      _profile() → CALIBRATED_CONFIDENCE
  (when ff.enabled() is False)                   (when ff.enabled() is True)
```

Selection happens once per `compute()` call via `_profile()` which checks
`core.feature_flags.enabled()`. The class-level constants (e.g.
`ConfidenceEngine.CAP_CONFIRMED`) remain the frozen v4.2 values so legacy
callers/tests observe the frozen contract unconditionally; only the instance path
is gated.

## 2. Calibration changes (Before / After)

### 2a. Cap reconciliation (C1)

| Cap | Frozen (v4.2) | Calibrated (v4.3) | Verification band threshold | Note |
|-----|---------------|-------------------|----------------------------|------|
| CAP_EXPLOITED | 100 | 100 | — | Unchanged |
| CAP_VERIFIED | 90 | **95** | 95 (CONFIRMED) | Verified evidence can now reach 'confirmed' band |
| CAP_CONFIRMED | 85 | **95** | 95 (CONFIRMED) | Confirmed evidence can reach 'confirmed' band |
| CAP_LIKELY | 75 | **80** | 80 (LIKELY) | Likely evidence now aligns with LIKELY band |
| CAP_POSSIBLE | 60 | **55** | 55 (POSSIBLE) | Aligned exactly with POSSIBLE threshold |
| CAP_ERROR | 40 | 40 | — | Unchanged |

Before: `confirmed` evidence capped at 85, needing 95 for 'confirmed' band →
could never be classified 'confirmed', stalling at 'likely' or 'possible'.
After: cap matches threshold, so evidence CAN reach the correct band.

### 2b. Evidence quality blend (C2)

Previously `evidence_quality` (computed by `EvidenceEngine.score()`) was recorded
on the finding but **never consumed by any scoring logic**. The calibrated path
blends it directly into the confidence base:

```
quality_base = evidence_quality                (when EVIDENCE_QUALITY_WEIGHT = 1.0)
base = max(legacy_base, quality_base)
```

This means rich evidence (confirmed + payload + snippet + verification passes →
quality 85–90) lifts confidence directly, which the old bonus-based path did not
capture because per-evidence bonuses are coarse (20 per confirmed) and do not
distinguish between confirmed-with-payload vs confirmed-without.

## 5. Rationale for each adjustment

### CAP_VERIFIED 90→95
Reconciled with `VerificationEngine.CONFIRMED_THRESHOLD` (95). A finding with
`verified` evidence (hard-classified as 'confirmed' by the verification override)
can now reach 95, matching its semantic meaning. Previously capped at 90, it
would be confidence 90→'likely' without the hard override.

### CAP_CONFIRMED 85→95
The main C1 fix. Confirmed evidence (without exploited/verified hard override)
was capped at 85, below the 95 'confirmed' band threshold, so it always fell
to 'likely' or 'possible'. Raising the cap to 95 allows confirmed evidence to
reach the 'confirmed' verification classification when confidence is high
enough (aided by evidence_quality lift).

### CAP_LIKELY 75→80
Aligned with `LIKELY_THRESHOLD` (80). Previously a likely-capped finding at 75
would classify as 'possible' (<80). Now at 80, likely evidence reaches 'likely'.

### CAP_POSSIBLE 60→55
Aligned with `POSSIBLE_THRESHOLD` (55). Possible-capped findings at 60 still
classified as 'possible' (≥55) but the cap was unnecessarily high. Lowering to 55
keeps POSSIBLE at its threshold, so any finding capped at possible will always
stay in 'possible' or below.

### EVIDENCE_QUALITY_WEIGHT 1.0
Direct lift from the currently-unused `evidence_quality` signal (audit C2). Weight
1.0 means `quality_base = evidence_quality` replaces the legacy base when higher.
This brings the rich contextual signal (payload presence, snippet, parameter,
verification passes) into the confidence calculation — previously these only
affected `evidence_quality` but not confidence.
